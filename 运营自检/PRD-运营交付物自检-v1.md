# Part 0 — 方法论基础

## 0. 为什么沿用这套流程

传统软件产品的逻辑是确定性的，输入什么就输出什么。AI 产品的输出是概率性的，因此流程里多出一段"算法模型生命周期管理"。

这个项目的特殊之处在于：**它最终选择不使用大模型。** 因此流程里"模型预研"一节被替换为"技术方案选型"，专门论证为什么规则引擎比大模型更适合这个场景。

流程的六个环节保留不变，因为每一步都要产出东西：

| 环节 | 产出物 | 本项目对应 |
| --- | --- | --- |
| 需求定义 | 问题定义、目标用户、成功指标、约束 | 第 1 节 |
| 算法预研 | 技术选型、可行性评估 | 第 2 节 |
| 数据准备 | 输入字段、输出格式、知识对照 | 第 3 节 |
| 逻辑构建 | 工作流、判定规则、异常处理 | 第 4 节 |
| 评测标准 | 评分维度、评测方法、验收线 | 第 5 节 |
| 开发上线 | 功能模块、技术实现、迭代路线 | 第 6、7 节 |

# Part 1 — 完整 PRD

## 1. 需求定义

### 1.1 项目背景与业务价值

**背景一：运营的时间大量消耗在核对类工作上。**

一份公开分享的在职运营日程显示，一天五个时段里有四个都是"收集、整理、核对、同步"：每日数据复盘、玩家反馈收集与分类归档、当日工作清单梳理、配置与文案核对。真正需要创造性判断的份额不高。

**背景二：这类工作最怕两件事。**

一是**漏项**。原始要求里逐项列出的内容，只要有一条没落地，交出去就是缺项，被退回重做。
二是**数字站不住**。写了一个没有出处的数字，被追问时答不上来；把第三方估算写成内部数据，内行一眼看穿。

**背景三：现有方案补不上这一段。**

已落地的 AI 方案集中在洞察层——从海量数据里看趋势，且基本都是企业级采购。而执行层的逐项核对，还是人在做。这两件事不是一回事。

**业务价值：** 把交付前的核对从"靠人记得住"变成"机器逐项过一遍"。机器负责查齐不齐、对不对、口径统一不统一，人负责改和判断。

### 1.2 目标用户与使用场景

| 用户 | 特征 | 需求 |
| --- | --- | --- |
| 主用户：执行层运营 | 每天要交多份材料，内容重复度高，最容易漏项 | 交出去之前有个东西帮着过一遍 |
| 次用户：运营负责人 | 要验收下属交上来的材料，逐份细看不现实 | 快速看出哪份材料有硬伤 |

**三个典型场景：**

**场景一　每日玩家反馈分类表交出去之前。** 需要确认分类是否互斥、是否穷尽、缺陷与建议有没有分开统计。分类口径不一致，后面汇总出来的结论就是错的。

**场景二　版本更新公告上线之前。** 需要确认时间与版本号是否与实际一致、奖励数量与道具名称是否与配置一致、有没有出现绝对化或承诺性的表述。

**场景三　配置核对清单提交之前。** 需要确认弹窗、入口、后台参数、开关服时间是否逐项列出，出问题时能不能定位到谁在什么时候核过。

### 1.3 现有方案分析

| 方案 | 覆盖的层 | 形态 | 本项目的差异点 |
| --- | --- | --- | --- |
| Sprinklr | 洞察层，情感分析 | 企业级采购 | 它看趋势，本项目查完整性 |
| 数数科技数据洞察 | 洞察层，舆情与画像关联 | 企业级采购 | 同上 |
| 智谱 AI 游戏方案 | 买量创意、舆情、社交安全 | 企业级采购 | 同上 |
| Helpshift | 客服自动化 | 企业级采购 | 面向玩家侧，本项目面向内部交付 |
| 通用大模型文本检查 | 语义层 | 对话式 | 结果不可复现，不适合做质检 |

**空档位置：** 现有方案全部站在"分析"这一侧，没有人站在"交付前最后一道关"这一侧。而这个位置的特征恰好适合机器：检查项固定、重复发生、出错代价大。

### 1.4 成功指标与验收标准

| 指标 | 定义 | 验收线 |
| --- | --- | --- |
| 检出率 | 样例集中注入的已知问题，被检出的比例 | ≥ 90% |
| 误报率 | 报出的问题中，实际不构成问题的比例 | ≤ 10% |
| 栏目覆盖 | 该类型交付物的必检栏目，实际执行检查的比例 | 100% |
| 单次运行时间 | 从运行到出报告 | ≤ 3 秒 |
| 长期指标 | 使用后交付物被退回重做的次数变化 | 待上线后采集 |

**说明：** 前四项在 v1 阶段可以立即测；第五项需要真实使用数据，列为后续观测项。

### 1.5 约束条件

1. **单机运行，不联网。** 交付物往往含未公开的版本信息和数据，不能上传。
2. **只读，不修改原文件。** 检查工具改动原稿是不可接受的风险。
3. **规则可配置。** 不同项目的提交规范不一样，规则必须能改，且改规则不用改代码。
4. **不改变既有工作流。** 它是最后一道检查，不进入生产流程，不替代任何现有环节。
5. **零成本。** 不依赖任何付费接口或云服务。

## 2. 技术方案选型

### 2.1 为什么这个场景不用大模型

这是本项目最关键的一个技术判断，需要说清楚。

| 维度 | 大模型方案 | 规则引擎方案 | 本项目选择 |
| --- | --- | --- | --- |
| 结果可复现 | 同一输入两次运行结果可能不同 | 完全一致 | **规则** |
| 可审计 | 无法解释为什么报这一条 | 每条对应一条明确规则 | **规则** |
| 离线可用 | 需要联网调接口 | 单机运行 | **规则** |
| 成本 | 按调用计费 | 零 | **规则** |
| 数据安全 | 内容需上传 | 不出本地 | **规则** |
| 语义理解 | 强，能读懂意思 | 弱，只认字面 | 大模型 |

**结论：** 质检场景要的是"每一次结论一致、每条都能解释来源"。大模型在这一点上恰恰是弱项。**用大模型做质检，等于用一个每次结果不同的尺子去量长度。**

### 2.2 规则引擎的适用边界

明确说清能力与不能力：

**能做：** 形式完整性。该有的栏目有没有、数字有没有标来源、有没有禁用表述、同一指标前后数值是否一致、引用有没有出处。

**不能做：** 语义正确性。这段表述是否准确、这个结论是否成立、这句话会不会让玩家误解。这些必须人来看。

**边界处理方式：** 把"机器能判的"和"必须人判的"在输出上分开。机器只报事实（第几行、什么内容、触发了哪条规则），不下"合格/不合格"的判断。

### 2.3 数据可行性

**输入数据：** 待检交付物本身（Markdown 或纯文本）。不需要任何外部数据源，不依赖数据库、不依赖历史积累。

**规则数据：** 四类交付物的检查规则，来源是岗位公开描述与行业公开资料，写在配置文件中，附来源说明。

**已知限制：** 规则来自公开资料，尚未经过真实业务数据校准。这项在迭代路线里列为待办。

## 3. 检查项设计

### 3.1 四类交付物与检查项

| 交付物 | 检查项 | 规则来源 |
| --- | --- | --- |
| 版本更新公告 / 游戏内文案 | 必含栏目（含概率公示）、绝对化用语、承诺性表述、数字出处、时间与版本一致性 | 岗位要求原文；行业清单：内容与数据合规 |
| 玩家反馈分类表 | 来源渠道、分类维度、可复现性、影响范围、缺陷与建议是否分列 | 岗位要求原文：分四类归档，过滤情绪发言，保留可落地的事实描述 |
| 配置核对清单 | 弹窗、入口、参数、开关服、回滚、核对人留痕、关键接口、埋点 | 岗位要求原文；行业清单：关键接口安全、数据埋点完整性 |
| 活动复盘 / 分析报告 | 目标、指标口径、结论、优化项、异常场景覆盖 | 岗位要求；行业清单：灰度反馈闭环 |
| 版本上线自检 | 客户端、接口、埋点、活动规则、处置分级、客服申诉、内容审核、数据合规、回滚、归档 | 行业清单：游戏上线前安全自检、上线全流程、发布前检查清单 |

**关于规则来源：** 带"行业清单"字样的检查项，是从公开的行业成熟清单中提取的，不是本项目自行推演的。提取时只取可迁移的**检查维度**，不照搬其判定阈值——行业清单面向的是整个游戏上线，本项目面向的是运营交付物流转前的自检，粒度不同，需要按场景重新组织。

### 3.2 规则配置结构

规则写在 `checklist.json`，结构如下：

```
deliverable_types
  └─ <类型键>
       ├─ name                 类型名称
       ├─ source_note          岗位依据（可追溯）
       ├─ industry_sources     行业清单来源（可追溯）
       ├─ required_sections    必含栏目
       ├─ forbidden_wording    禁用表述
       ├─ soft_wording         空泛表述（建议级）
       └─ notes                重点核对提示

global_rules
  ├─ source_markers       来源标记词
  ├─ uncertain_markers    待验证标记词
  └─ unit_pattern         数量单位（A 与 D 两个检查共用）
```

**设计要点：`unit_pattern` 被两个模块共用。** 这一点来自实际踩坑：初版 D 检查把单位列表硬编码在脚本里，与 A 检查各写一份，结果 A 能识别"星琼"而 D 不能，导致一致性检查静默失效。改为共用同一份定义后，这类问题不会再出现。

### 3.3 输出格式

每个模块输出一份 JSON，字段固定为：

| 字段 | 含义 |
| --- | --- |
| level | 严重度：需修改 / 缺项 / 需核对 / 待确认 / 建议 |
| line | 出现在第几行 |
| text | 原文片段 |
| issue | 触发了哪条规则 |
| suggest | 建议怎么改 |

外加一份 `00_汇总.txt`，列出各模块结果与待处理项总数。

## 4. 检查逻辑设计

### 4.1 工作流

```
读取配置 checklist.json
        │
        ├─→ A 数据检查      数字是否带出处
        ├─→ B 表述检查      禁用词与套话
        ├─→ C 结构检查      必含栏目是否齐全
        ├─→ D 一致性检查    同一指标是否多值
        └─→ E 来源检查      引用是否带出处
        │
    汇总 → output/00_汇总.txt
```

五个模块互相独立，任一模块报错不影响其余模块执行。

### 4.2 各模块判定逻辑

| 模块 | 判定方式 | 触发条件 |
| --- | --- | --- |
| A 数据检查 | 正则匹配数量型数字 | 行内出现数字但既无来源标记词，也无待验证标记词 |
| B 表述检查 | 关键词匹配 | 命中该交付物类型的禁用词或软性词 |
| C 结构检查 | 全文关键词存在性 | 该类型必含栏目在全文未出现 |
| D 一致性检查 | 提取「名称＋数值」对并聚合 | 同一名称关联到两个以上不同数值 |
| E 来源检查 | 正则提取引号内容 | 行内有引用但无来源标记词 |

### 4.3 异常与边界处理

1. **待检文件不存在。** 不中断，输出明确提示，其余模块继续运行。
2. **配置缺少某类型。** 该类型的检查项按空处理，不报错。
3. **数字正则会误抓格式性数字。** 通过限定"数字必须带单位"来降低噪音：版本号 4.6、日期 2026 这类不带单位的不会被抓。
4. **D 检查对书写格式敏感。** 名称与数值之间必须有"为/是/："这类连接符，写法过于自由时抓不到。这是已知限制，写在 README 的边界一节。

## 5. 评测标准

### 5.1 评测维度

| 维度 | 定义 | 权重 |
| --- | --- | --- |
| 检出率 | 已知问题被检出的比例 | 高 |
| 误报率 | 报出的问题里不成立的比例 | 高 |
| 栏目覆盖 | 必检栏目实际执行的比例 | 中 |
| 运行性能 | 单次运行耗时 | 低 |

### 5.2 评测方法

采用**注入法**：构造一份包含已知问题的样例交付物，问题的类型与数量事先登记，然后运行检查，比对结果。

样例设计原则：
1. 覆盖全部五个模块，每个模块至少注入两处问题
2. 同时包含**正常表述**作为对照，用于测误报
3. 问题尽量贴近真实写法，不使用刻意构造的畸形文本

**首轮结果：** 单份样例注入 12 处问题，实测检出 12 处。首轮暴露了一个真实缺陷——D 模块因单位表硬编码而漏检。

**扩展后结果：** 样例集扩充为四份，分别对应公告、玩家反馈日报、活动复盘报告、版本上线自检，共注入 38 处问题。首跑检出 37 处，漏检 1 处。

**第二次漏检根因：** A 模块的数量单位白名单里没有「项」，样例四的「42 项」因此没被抓到。这与第一次漏检同源——都是**枚举型白名单不全导致的静默失效**。

**修复方式：** 补全单位白名单。同一类问题到此已出现三次（硬编码单位表、指标名称未归一化、单位白名单不全），所以处理方式不是逐个补词，而是**把共用定义收拢**：单位表由 A 与 D 两个模块共用同一份，名称归并统一在 D 内部处理。

**漏检根因：** 样例三中「活动期间参与率：32%」与「参与率：45%」指向同一指标，但 D 模块按名称聚合时，把前者识别为「活动期间参与率」、后者识别为「参与率」，两个名称对不上，因此没有触发多值告警。这不是规则写错，是名称匹配的粒度问题。

**修复方式：** 在 D 模块加入名称归一化——短名称若是某个长名称的子串，归并到最长的那个名称。修复后复跑，31 项全部检出，无漏检、无疑似误报。

**为什么分两轮：** 第一轮用注入法建立基线，目的是先排除规则自身的缺陷——如果规则连刻意构造的问题都抓不到，拿真实材料去测就没有意义。第二轮用真实业务材料校准，因为真实写法比样例自由得多，名称、格式、表述都不会像样例这样规整，规则需要按实际语义再调一轮。第二轮列入 v1.2。

### 5.3 验收标准

| 项 | 标准 |
| --- | --- |
| 检出率 | ≥ 90% |
| 误报率 | ≤ 10% |
| 栏目覆盖 | 100% |
| 运行时间 | ≤ 3 秒 |
| 原文件改动 | 必须为零 |

## 6. 功能开发

### 6.1 功能模块

| 模块 | 文件 | 职责 |
| --- | --- | --- |
| 调度 | `run_all.py` | 依次运行五个检查，汇总结果 |
| 公共 | `common.py` | 读配置、读文件、统一输出格式 |
| A 数据检查 | `A_number_check.py` | 数字出处 |
| B 表述检查 | `B_wording_check.py` | 禁用词与套话 |
| C 结构检查 | `C_structure_check.py` | 栏目覆盖 |
| D 一致性检查 | `D_consistency_check.py` | 指标多值 |
| E 来源检查 | `E_source_check.py` | 引用出处 |
| 规则 | `checklist.json` | 全部检查规则 |

### 6.2 用户旅程

```
准备交付物 → 改 checklist.json 的 target 指向它 → 运行 run_all.py
    → 看 output/00_汇总.txt 知道几项待处理
    → 逐项看各模块报告，按其「建议」列修改
    → 改完重跑 → 待处理项归零 → 交付
```

### 6.3 输出设计

命令行输出采用固定格式：模块名 → 逐条列出（严重度、行号、原文、问题、建议）→ 合计项数。设计取舍是**每条都要能落到"改哪里、怎么改"**，只报问题不给建议的检查结果没有用。

### 6.4 非功能需求

| 项 | 要求 |
| --- | --- |
| 兼容 | 常规 Python 3 环境，无第三方依赖 |

## 7. MVP 范围与迭代路线

| 版本 | 范围 | 状态 |
| --- | --- | --- |
| v1.0 | 五项检查、四类交付物、规则配置化、命令行报告 | 已完成 |
| v1.1 | 样例集扩充至 30 处以上注入；按结果反推规则误报并调优；补充第五类交付物（竞品简报） | 待做 |
| v1.2 | 用真实业务材料校准规则；输出支持导出为可直接发给同事的清单 | 待做 |
| v2.0 | 引入语义级检查：对"这句公告会不会让玩家误解""这个结论是否成立"这类问题，接入大模型做辅助判读，与规则结果分列展示 | 待做 |
| v2.1 | 与协作工具对接，支持批量检查一个目录下的多份交付物 | 待做 |

**划入不做：**

- 自动修改原文件。质检工具动原稿的风险远大于收益。
- 输出"合格/不合格"的整体判断。这个判断权必须留在人手里。
- 竞品信息收集。调研显示这项依赖人情交换，不是工具能解决的。

## 8. 附录

### 8.1 术语表

| 术语 | 含义 |
| --- | --- |
| 交付物 | 运营需要交给同事、上级或对外发布的成品材料 |
| 栏目覆盖 | 该类型交付物规定的必含部分，是否都在材料中出现 |
| 注入法 | 往样例里预先放入已知问题，用来测工具能检出多少 |
| 检出率 / 误报率 | 前者衡量漏没漏，后者衡量冤不冤 |
