# 运营交付物自检

把运营每天要交出去的东西，在交出去之前过一遍机器检查。

**为什么做这个。** 运营的日常里，大量时间花在收集、整理、核对、同步上。这些是执行工作，不是判断工作。AI 现阶段最能派上用场的地方，就是把这一类重复执行做成自动化，把人从里面解放出来，让他们把精力放在真正需要判断的事情上。

这个工具替掉的是其中最机械的一段：逐项核对。

---

## 一、这是给谁用的，解决什么问题

运营岗的日常里，大量时间花在"收集、整理、核对、同步"上。调研一份在职运营人员的公开日程可以看到，五个时段里有四个都是这类动作，真正需要创造性判断的占比不高。

而这些动作最怕两件事：**漏项**和**数字站不住**。漏了一项，东西被退回重做；写错一个数，被追问时答不上来。

现有 AI 方案（Sprinklr、数数科技、智谱、Helpshift 等）解决的是"从海量数据里看出趋势"，属于洞察层，基本都是企业级采购。而执行层的核对工作，还是手工在做。这个自检脚本补的就是这一段。

**定位：机器负责把该核的都核一遍，人负责改和判断。**

---

## 二、怎么用

```
python run_all.py
```

跑完之后，结果在 `output/` 目录里：六个检查各出一份 JSON，另有一份 `00_汇总.txt`。

**脚本只读待检文件，不会修改任何内容。**

换一份待检文件：改 `checklist.json` 里的 `target` 和 `target_type` 两个字段即可。

---

## 三、六个检查分别查什么

| 模块 | 查什么 | 为什么查这个 |
| --- | --- | --- |
| A 数据检查 | 所有数量型数字，是否带来源标注或待验证标注 | 数字没出处，被追问时答不上来；把第三方估算写成内部数据，内行一眼看穿 |
| B 表述检查 | 绝对化用语、承诺性表述、空泛套话 | 公告里的"永久""必得"有合规风险；套话让读者看不到具体信息 |
| C 结构检查 | 该类型交付物要求的栏目是否齐全 | 漏项是交付物被打回的头号原因 |
| D 一致性检查 | 同一指标在文中是否出现多个不同数值 | 前后打架，整份材料的可信度就没了 |
| E 来源检查 | 引用的玩家发言或数据，是否标了出处 | 引用查不到，等于没有证据支撑 |
| F 列举检查 | 写「共 N 条」时，后面实际列出的项数是否等于 N | 实测里出现过写「共 4 条」却列 5 个；这类错不需要判断力，数一遍就行，正好交给机器 |

## 四、规则放在哪

全部规则写在 `checklist.json` 里，**改规则不用改代码**。

- `deliverable_types`：六类交付物各自的必含栏目、禁用词、软性词，以及规则来源
  - `announcement` 版本更新公告与游戏内文案
  - `feedback_table` 玩家反馈分类表
  - `config_checklist` 配置核对清单
  - `reward_check` 奖励发放核对表
  - `report` 活动复盘与分析报告
  - `launch_check` 版本上线自检
- 每类都带 `source_note`（岗位依据）与 `industry_sources`（行业清单来源）。**带行业来源的检查项不是自己推演的**，是从公开的成熟清单里提取的。例如"处置策略要分级：观察、验证、限制、复核、隔离、处置"这一条，原文与出处见 `行业检查清单索引.md`
- `global_rules`：数字单位、来源标记词、待验证标记词

每一类交付物的规则里都附了 `source_note`，写明这条规则是从哪来的，出问题时可追溯。

## 五、当前边界

说清楚不能做什么，免得被误用：

1. **它不判断内容对不对，只判断该有的有没有。** 具体事实是否准确，仍要人回官方来源核对。
2. **规则是关键词匹配，不是语义理解。** 换个说法就绕过去了，所以它只适合当第一道筛子，不能替代人工复核。
3. **D 检查的指标识别依赖"名称＋数值"的书写格式。** 写法太自由时抓不到，属于已知限制。
4. **四类交付物的规则来自岗位公开描述与行业公开资料**，还没有经过真实业务数据校准，需要在实际使用中迭代。

## 六、怎么测效果

```
python eval.py
```

评测用**注入法**：`golden/` 下的三份样例事先注入了已知问题，清单登记在 `golden_truth.json`。脚本逐份跑检查，比对哪些被检出、哪些漏了，报告写到 `output/99_评测报告.txt`。

**当前结果：** 四份样例（公告、反馈日报、复盘报告、上线自检），注入 38 项，检出 38 项，无漏检、无疑似误报。

**评测分两轮走。** 第一轮就是现在这轮，用注入法建立基线，目的是先排除规则自身的缺陷——如果连刻意构造的问题都抓不住，拿真实材料去测就没有意义。第二轮用真实业务材料校准，因为真实材料里的写法比样例自由得多，名称、格式、表述都不会这么规整，规则要按实际语义再调一轮。第二轮已列入迭代路线 v1.2。

评测过程修掉了三个真缺陷，**三个是同一类问题**——枚举型规则没定义全，导致静默失效：

1. D 模块的单位表硬编码，与 A 模块各写一份，导致 A 认得"星琼"而 D 不认。改为共用 `checklist.json` 里的 `unit_pattern`。
2. D 模块按名称聚合指标时，「活动期间参与率」与「参与率」对不上，漏掉一处矛盾。加入名称归一化：短名称若是长名称的子串，归并到长的那个。
3. A 模块的单位白名单漏了「项」，样例四的「42 项」没被抓到。补全白名单。

第三个修完之后，处理方式从"逐个补词"改成**收拢共用定义**：单位表由 A 与 D 共用一份，名称归并统一在 D 内部做。同一类问题连出三次，说明问题不在词表，在结构。

## 七、目录结构

```
运营自检/
├── run_all.py                一键运行六项检查
├── eval.py                   评测：算检出率与误报率
├── A_number_check.py         数据检查
├── B_wording_check.py        表述检查
├── C_structure_check.py      结构检查
├── D_consistency_check.py    一致性检查
├── E_source_check.py         来源检查
├── common.py                 公共工具
├── checklist.json            检查规则（可改，含行业来源标注）
├── golden_truth.json         评测集：登记样例里注入的问题
├── golden/                   评测样例（四份）
├── sample/                   演示用样例
├── 行业检查清单索引.md        扒来的行业清单原文摘录与映射
├── PRD-运营交付物自检-v1.md  产品需求文档
└── output/                   检查报告输出
```
